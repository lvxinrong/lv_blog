这套 Skill 有 187 行指令、11 个脚本、4 份规范文档，但翻遍整个仓库，**你不会找到一句话教 AI「怎么排查生产问题」**。

没有「第一步查日志、第二步看监控、第三步读源码」，没有「遇到超时先怀疑连接池」，也没有任何一个排查框架、根因树、决策表。

这是故意的。我在工程手记里写过它的设计哲学（[生产排查，不该是『老师傅』的手艺](/craft/prod-debugging/)），但那句话太像口号了，今天把实现拆开给你看。这套 Skill 的全部内容，其实只有三样东西：**现场、边界、验收**。

## 一、为什么「不教排查」

刚做这套东西的时候，我也想过把排查流程写细：先查 SLS，再拉 Trace，再定位服务，再翻代码。真写下去就会发现这条路是死的。

**每起事故都是新的。** 一次 Doris FE 资源耗尽和一次移动端证书失效，证据的位置、查询的顺序、需要的工具完全不同。把流程写死，轻则让 AI 做一堆无用功，重则把它带进沟里——它会在「第一步」找不到证据时，硬编一个答案来交差。

所以 SKILL.md 里只有一句原则性的话：

> 本 Skill 只提供现场、工具和必要的安全约束。Agent 可以根据具体事故自主决定排查思路、工具组合和证据顺序。

**过程自由，契约刚性。** 排查的路让 AI 自己走，但现场必须可复现、权限必须只读、结论必须可审计。这和教育的道理一样：好老师不替学生走路，好老师修操场、立规矩、改卷子。

想清楚这一点，Skill 的三段式结构就出来了。

## 二、第一段：环境就绪——「装了」不等于「能用」

AI 排查失败的头号原因不是模型不行，是**现场不行**：日志平台没配、源码是旧的、代码图谱没索引、数据库连不上。模型面对这些，不会说「我查不了」，它会直接开编。

所以这套 Skill 把「环境就绪」做成了一道**强制门禁**，而不是一句「请确保环境可用」。

### 一次检查，全部状态摆出来

`scripts/check-environment.sh` 用稳定的 TSV 状态行，一次汇总所有能力：阿里云 CLI 是否就绪、SLS 和 ARMS 是否实际可读、本地源码最近同步状态、代码图谱索引是否覆盖全部托管仓库。最后只有两种汇总：`ENVIRONMENT_CHECK_READY` 或 `ENVIRONMENT_CHECK_PARTIAL`。

注意「实际可读」这四个字。脚本不是检查「命令存在」，而是真的去读一次——**能 ls 和能 read，是两回事**。

### 状态必须分层，因为「部分就绪」最危险

这套状态机里最值钱的设计，是把「就绪」拆得很碎。随便举几个：

- `CODEBASE_MEMORY_LOCAL_READY`：只代表本地程序装好了，**不代表**当前 Agent 会话里 MCP 工具可用，**更不代表**相关仓库有索引
- `CODEBASE_MEMORY_RESTART_REQUIRED`：MCP 配置写进去了，但当前会话没加载，需要重启 Agent
- `SOURCE_REFRESH_IN_PROGRESS`：源码正在刷新，**禁止**读取受管源码、禁止调用图谱

为什么要这么细？因为 AI 最擅长把「部分可用」说成「一切正常」。`LOCAL_READY` 这个名字看起来就很像「就绪」，如果不加区分，Agent 就会拿着一个「装了但没索引」的图谱去下源码结论。

所以门禁里还有一条硬性规定：**shell 脚本无法证明当前会话加载了 MCP 工具，Agent 必须实际调用一次 `list_projects`，调不通就把状态改回 `PARTIAL`，不许声称图谱可用。** 验证永远以「真的调了一次」为准，不以「理论上应该有」为准。

### 源码新鲜度：排查的是「线上那个版本」，不是「我本地这个版本」

生产事故最常见的弯路，是拿最新代码分析旧事故。这套 Skill 对源码版本有三道锁：

1. **排查开始时，后台全量对齐**（`refresh-sources.sh`），不阻塞其他证据收集；**读取源码前，必须通过新鲜度门禁**（`await-freshness.sh`），刷新没完成就不许读、不许查图谱
2. **以刷新完成时各仓库的 HEAD Commit 作为本次排查的源码基线**，排查期间不再二次刷新；报告里每个仓库都记录精确 Commit
3. **对齐不了事故版本时，必须写明「当前源码已检查，事故版本尚未确认」**，不许把当前源码行为直接当作线上事实

「我查过源码了」和「我查过**那个版本**的源码了」，是两份完全不同的证据。

### 范围闭合：不许说「源码不可用」来甩锅

还有一条专门防偷懒的：当证据链指向客户端、网关或上下游组件时，**必须先核对受管仓库里有没有它**，完成一次有边界的检索（接口路径、方法名、错误文本），才能下「未纳入」的结论。日志里出现 `platform=android`，就得去核对 Android 仓库，不能因为告警发生在服务端就默认客户端无关。

> 不要把「Agent 尚未检查」写成「源码不可用」。

「没查」和「没有」，在事故报告里是两回事。

## 三、第二段：只读——不靠「嘱咐」，靠「结构」

让 AI 接触生产环境，我最担心的从来不是它查得慢，是**它顺手做点什么**。所以只读不是靠提示词里写「请不要修改生产数据」——那是一句废话，模型手一抖就是事故。只读必须长在结构里。

### 包装脚本：把「只能读」做成默认路径

所有云端调用都走包装脚本，不开放原始命令：

- `aliyun-sls.sh`：自动注入固定的生产 Project 和 Endpoint，**拒绝通过参数覆盖**——想查错环境？参数层面就不允许
- `aliyun-arms.sh`：只放行排查需要的**只读 API**，强制关闭 CLI 插件自动安装
- `aliyun-prod.sh`：拒绝覆盖凭据、Profile、Token 和地域

阿里云配置也是 Skill 独立的一份，放在自己的配置目录里，**不碰用户日常使用的 CLI Profile**。这样 Skill 用的身份是架构专门开的只读账号，而不是我日常那把什么都能干的钥匙。源码同步用专用的只读 SSH 私钥，同样不修改全局 SSH 配置。

原则就一条：**让「只读」成为默认路径，让「能写」成为不存在的路径。**

### DBX：fail closed，宁可不查

数据库是可选能力，闸门更严。`dbx-readonly-policy.md` 规定：

- **工具面白名单**：只许出现查询类工具。如果发现连接管理、数据修改、DDL、导入导出等任何非只读工具，直接 `DBX_PERMISSION_SCOPE_INVALID`，停止全部 DBX 调用
- **SQL 白名单**：只接受 `SELECT` / `SHOW` / `DESCRIBE` / `EXPLAIN` 开头的单条语句，其他前缀一律拒绝。禁止 `SELECT *`，返回最多 100 行，大表先 EXPLAIN
- **权限不明，就不查**：无法确认只读策略已生效，不查；**绝不允许用「试写一下再回滚」来验证权限**——验证权限这件事本身就可能造成事故
- 数据库证据没拿到，就明说「未纳入」，**其他证据继续查，但不许把数据库假设写成根因**

这就是 fail closed：任何一环存疑，闸门自动落下，而不是「先用了再说」。

## 四、第三段：输出契约——AI 负责分析，规范负责「不许糊弄」

现场备齐、边界锁死，剩下的分析过程完全放开。但最后交出来的东西，必须过 `incident-analysis-output.md` 这道关。这份 210 行的规范，是整套 Skill 里我最得意的部分——**它不教怎么查，它只管「不许糊弄」**。

### 结论状态只有四种，没有「80% 确定」

- `已确认`：直接证据闭合关键因果链，且无冲突证据
- `高置信`：多个独立证据一致支持，只剩非关键环节未直接验证
- `待验证`：有可检验的假设，关键环节还没证据
- `证据不足`：撑不起可靠判断

规范明确禁止「缺乏依据的百分比置信度」。「80% 确定」这种话，是把证据的缺口包装成数字，看起来很专业，实则不诚实。

还有一条很狠的：**总体状态不得高于最弱的关键环节**。服务端链路已确认、端到端根因待验证，那就得分开写——「下游查清了」不等于「整件事查清了」。

对「死锁、行锁等待、内存溢出」这类**机制级**判断，只有日志、Trace、监控直接呈现该机制时才能标「已确认」；时间顺序和源码语义都吻合但没直接证据，只能是「高置信」。**推测出来的机制，不能享受目击者的待遇。**

### 原因必须分四层，不许一个「根本原因」包打天下

- **直接原因**：直接导致告警或异常的系统行为
- **上游触发**：让直接原因成立的请求、流量、操作
- **缺陷或放大因素**：没拦住异常的代码、配置、架构缺陷——**保护性校验缺失，不等于异常最初产生的原因**
- **最终根因**：能解释「异常最初为什么产生」的那个原因

很多事故复盘写不好，就是把这四层揉成一锅：异常抛出点当了根因，缺防御当了根因，真正的上游触发反而没人追了。

### 事实、推断、建议，三样东西分开摆

「客观事实」列只写直接观测，「支持的判断」列写这个证据能推出什么。**时间相关性不能写成因果，源码语义不能写成线上事实，用户描述不能写成系统事实。**

最见功力的是这一条：**所有否定性、穷尽性判断，都必须带上查询边界**。「无其他影响」「未发现异常」「全部服务正常」——写这些的时候必须附上：哪个数据源、哪个应用、哪个时间窗口。**「查询窗口内未检出」不等于「整个生产不存在」**——这句话几乎是为所有 AI 生成的复盘报告量身定制的。

报告的第一屏永远是「事故结论卡」：结论状态、已确认范围、未确认范围、故障位置（仓库/Commit/文件/行号）、下一步。**可以独立阅读，不许强迫读者翻十页找结论。**

### 验收清单：20 多条「不许」

规范最后是一份质量检查清单，全是防糊弄的硬条款，随手摘几条：

- 没有把工具调用成功，等同于根因已经确认
- 没有把「尚未检查」写成「源码未纳入」
- 没有使用「已自愈」「无残留」「无需修复」等没有当前状态证据的表述
- 没有把建议写成已经执行
- 没有泄露凭据、私钥、Token

**模板允许空着，不许编。**「未确认」是一个合法的、受尊敬的答案。

## 五、这套 Skill 真正固化的是什么

回到开头那个问题：不写排查流程，那这套 Skill 的价值在哪？

我的答案是：**它固化的不是方法，是纪律。**

方法应该属于 AI——它比人更会在几十个服务、几千条日志里找关联，固化流程反而是束缚。但纪律必须属于工程：现场不齐不许开查、只读路径不许绕过、没有证据不许下结论、结论不全不许写「已确认」。

这三段连起来，就是我对「生产级」三个字的理解：

> **过程自由，环境可复现，权限只读，结论可审计。**

一个 Agent 聪不聪明，决定它排查的上限；这套纪律在不在，决定它排查的下限。而上限给老板看，下限才给生产用。
