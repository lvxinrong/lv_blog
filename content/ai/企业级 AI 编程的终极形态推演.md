> 让架构做架构，让开发做开发，让测试做测试，让运维做运维。
>
> 这篇文章是一种开放式推演，不是对行业终局的断言。我真正想讨论的是：**专业分工能否发生在模型训练层，而不只是 Agent 的角色编排层。**

## 从分词器想到企业研发分工

晚上读[《图解大模型》](/reading/illustrated-llm/)第二章，看到词元、特殊词元和文本嵌入，我一直在想一个问题：**模型理解世界的基本单元，会不会随着任务变化而变化？**

分词器把连续文本切成 token，再映射成 id。 token 是语言模型处理文本的基本单元，但在企业级开发中，我们日常打交道的基本单元往往不是 token，而是函数、接口、服务、组件和它们之间的依赖关系。

一个需求进入企业，通常会经过一条熟悉的流水线：架构师负责拆解与设计，开发负责实现，测试负责验证，运维负责发布和运行保障。

然而今天很多编程 Agent 的分工方式，是给同一个通用模型换一段提示词：

```text
你是一名资深架构师。
你是一名资深开发者。
你是一名资深测试工程师。
```

这当然有用，而且成本低、灵活、容易验证。但我也越来越清楚地看到它的边界：**提示词可以改变模型当下扮演的角色，却不等于模型在参数层面真正形成了不同的专业能力。**

于是产生了一个更激进的设想：未来企业级 AI 编程的分工，是否可以从通用模型出发，通过领域继续训练、微调和后训练，形成真正不同的专用模型？

不是 Agent A 扮演架构师、Agent B 扮演开发者，而是 A、B、C、D 在训练阶段就走向不同方向。

## 先放下一个诱人的简化：一个函数对应一个 token

这个思路最初是从“函数能不能成为 token”开始的。

代码高度结构化，又由大量短小的函数组合而成。如果能把一个原子化函数映射成一个 token id，模型面对需求时，是否就可以直接组合函数，而不必从底层逐 token 写代码？

这个想法很诱人，但很快会遇到泛化问题。企业里的函数数量庞大且持续变化，函数的语义还依赖参数、返回值、调用上下文、异常、事务和副作用。把它们全部固化进词表，就像试图给每句话分配一个 token：词表会膨胀，组合规律会消失，未见过的实现也难以表达。

所以更可行的路径不是把函数变成 token，而是：

> **把函数、API 和组件封装成模型可发现、可理解、可调用、可验证的能力单元，让模型生成调用与编排计划。**

组件仍然是可执行、可测试的工程资产，而不是词表里的静态条目。模型需要理解的是它们的契约和组合方式。

从这个角度看，企业级 AI 编程的关键就不只是 tokenizer，而是**模型如何理解组件、如何训练分工能力，以及如何通过工具完成真实交付。**

## 核心设想：分工发生在模型训练层

我设想中的四类模型，不是四个提示词 persona，而是四种可以用不同数据、训练目标和评估集分别优化的专用模型。

它们不必都从空白开始预训练。更现实的起点是通用底座，再根据角色进行领域继续训练、指令微调或后训练。关键不在于参数是否从零初始化，而在于：**能力是不是在训练过程中形成，而不是靠一句“你现在是专家”临时获得。**

### A：架构模型——学习怎样做系统判断

架构模型的训练数据，不应只有代码。它还需要企业系统文档、领域模型、架构决策记录、设计评审、优秀行业案例、事故复盘，以及方案被接受或否决的原因。

因为架构并不只是画出模块图。真正的架构能力包括：

- 把业务需求拆成边界清晰的系统能力；
- 判断哪些组件应该复用，哪些必须新建；
- 在一致性、性能、成本、复杂度和交付周期之间做权衡；
- 识别数据流、依赖关系和关键故障路径；
- 解释为什么一个看似优雅的方案，在当前组织里落不了地。

它的输出也不应只是“生成一份架构图”，而应包括组件契约、依赖约束、实施顺序、验收标准，以及关键取舍的证据。

这意味着架构模型需要自己的评估集。不能只看文字像不像专家，还要评估方案是否可执行、是否遗漏关键约束、是否过度设计，以及后续集成是否真的更顺利。

### B：开发模型——把契约变成可靠实现

开发模型负责把架构模型给出的函数契约变成代码。它更关注局部实现能力：算法、语言特性、仓库规范、错误处理、测试修复和代码可维护性。

它拿到的任务不应该只是一句“实现退款逻辑”，而应是一份足够明确的契约：

```text
输入和输出是什么？
允许依赖哪些组件？
异常和边界条件是什么？
性能与事务要求是什么？
必须满足哪些测试？
```

开发模型可以擅长把一个小而清晰的问题做好，不必同时承担整个企业的架构决策。架构模型也不应越界替它编造所有实现细节。

### C：测试与验收模型——学习怎样证明系统不值得信任

测试模型并不是简单地多生成几个单元测试。它需要学习怎样寻找需求与实现之间的缝隙：边界条件、并发竞争、数据异常、权限绕过、回归风险和“看起来对但其实不符合业务语义”的情况。

确定性验证仍应交给工具：编译器、测试框架、静态分析、覆盖率工具和性能压测。测试模型的价值在于设计实验、分析失败、判断证据是否充分，以及把问题反馈给正确的角色。

它还应具备一点“唱反调”的能力。否则开发模型交付什么，验收模型就赞美什么，这不是闭环，只是形式审查。

### D：运维模型——对系统上线后的行为负责

运维模型需要理解部署拓扑、配置、日志、指标、链路追踪、发布策略、回滚预案和运行手册。它的目标不是“把服务启动起来”，而是让变更在真实环境中可控地生效。

它应知道什么时候适合灰度，什么时候必须暂停发布，磁盘打满和 CPU 飙高分别可能关联哪些变更，以及什么证据支持回滚。

但运维模型的权限必须比建议能力更谨慎。模型可以给出诊断和操作计划，真正执行高风险动作仍需要确定性的策略限制、审批和审计。

## 三种信息，应该放在三个不同层次

这个设想最容易被误解的地方，是“把所有企业资料都拿去训练模型”。我认为需要把信息分成三层。

**模型权重：沉淀稳定的方法。** 例如架构原则、编码模式、测试方法、故障分析思路和行业优秀案例。这些适合通过训练形成能力。

**运行时上下文：描述正在变化的事实。** 当前仓库、实时架构图、服务依赖、线上指标、组织权限和配置状态，不适合只固化在权重里。它们更新快，而且直接决定当前判断是否正确，更适合由代码图谱、知识库、检索和工具实时提供。

**Agent 编排：推动角色与工具协作。** Agent 仍然重要，但不再只是把一句角色提示词塞给模型。它要负责路由任务、传递契约、调用工具、保存证据、控制权限，并在失败时决定反馈给哪个模型。

一句话概括：

> **权重负责内化方法，上下文负责描述当下，Agent 负责让协作真正发生。**

## 一次需求，怎样流过这支模型团队

假设要给订单系统增加退款能力。

架构模型首先读取当前系统结构和业务约束，判断退款应该独立成服务还是放在订单域内，给出状态流转、金额计算、幂等要求、事务边界和验收条件。它还要明确哪些现有组件可以复用，哪些缺口必须补写。

接着，运行时系统根据这份计划检索已有函数、API 和组件。能够复用的直接复用，不能复用的形成清晰的开发契约。

开发模型只负责补齐缺失部分，并提交实现和初步测试。随后，编译器和测试框架先执行确定性检查，测试模型再补充边界场景、审查失败证据，判断是否真的满足退款语义。

如果测试发现“金额可以退成负数”，问题返回开发模型；如果发现“现有订单状态机根本无法表达退款”，问题就应该返回架构模型，而不是让开发模型继续局部补丁。

最后，运维模型评估发布方案：数据库变更是否兼容、是否需要灰度、观察哪些指标、出现什么情况必须回滚。上线后的真实指标再反馈给整个系统。

这条链路里，**每个角色都可以被追问，每个结论都应该留下证据。** 模型分工的价值不在于显得更像一个组织，而在于让错误能够被路由到正确的层级。

## 为什么一定要分开训练？

通用模型继续变强，当然可能覆盖这些能力。所以“专用模型分工”不是必然答案，需要拿数据证明它是否值得。

它可能有几个优势：

- **训练目标更清晰**：架构模型不必为了生成漂亮代码而牺牲系统判断，测试模型也不必迎合实现；
- **评估更专业**：每个角色都能建立自己的基准，而不是只看最终代码能不能运行；
- **成本和时延可控**：部分任务可能由较小专用模型完成，不必所有请求都调用最大的通用模型；
- **独立升级**：代码模型升级不必同时改变架构和运维行为，更容易做回归；
- **职责与权限更容易治理**：架构建议、代码修改、验收结论和生产操作可以分别控制。

但代价同样真实：模型数量增加会带来部署、版本兼容、数据治理和接口维护成本。一个角色的错误还可能被下一个角色放大。接口如果定义不清，架构模型一句“这个很简单”，就可能让开发模型在错误契约上高速生产垃圾。

所以真正困难的也许不是训练出四个模型，而是**建立它们之间可靠、可验证、可追溯的协作协议**。

## 还要把训练成本的变化算进去

这个推演里还有一个会变化的变量：大模型本身的训练技术与硬件能力也在持续迭代。

我倾向于认为，**获得同等模型能力的单位训练成本，有望逐步下降。** 硬件算力、混合精度、分布式训练、显存优化、参数高效微调、数据质量和知识蒸馏都在发展。今天看起来昂贵的专用后训练，未来可能会成为更多企业可以承担的常规工程动作。

但这不等于“所有模型的训练总成本都会下降”。前沿模型仍可能通过更大的参数、数据和算力投入不断抬高上限。更准确的判断是：**同一能力的获取成本可能下降，而人类追求能力上限的总投入仍可能增加。**

这对专用模型分工是一个有利条件。架构、开发、测试和运维模型不必重复从零预训练，可以共享通用底座，只针对各自的能力缺口做继续训练和后训练。随着这类训练变得更便宜、更稳定，多专用模型的部署和维护成本也有机会下降。

因此，是否拆分模型不能只按今天的训练报价判断，还要同时看两条曲线：一条是专用训练能提升多少能力，另一条是获得这些能力的成本正在怎样变化。**当专用训练的收益足够明确，而单位成本持续下降时，模型团队才可能从少数机构的实验，变成普通企业也能选择的工程方案。**

## 可以从哪里开始验证

这条路不需要一上来就训练四个基础模型。更稳妥的做法是分三步：

第一步，先用同一个通用底座承担不同角色，把真实工作流跑通，保存需求拆解、架构方案、实现、测试失败、返工和最终验收数据。

第二步，用这些数据找出角色之间的能力差异。如果架构失败主要源于缺少企业判断，而不是缺少提示词，就针对架构模型做领域继续训练和专项评估；如果开发主要败在局部实现，就优化开发数据和测试反馈。

第三步，只有当专用训练在独立基准上稳定优于提示词角色，再拆分模型、独立部署。否则，一个强通用模型加良好编排，可能就是更经济的答案。

这也是我认为这条路线最科学的地方：**先证明分工确有必要，再为分工训练模型，而不是因为“模型团队”听起来先进就制造复杂度。**

## 终极形态，不是无人研发

我不认为企业级 AI 编程的终极形态只是“需求进去，系统出来”。需求本身有歧义，架构需要承担取舍，生产变更需要有人负责。人类仍然要决定目标、边界、风险接受程度，以及什么时候不该做一件事。

但模型承担的角色可能会真正发生变化：从统一的文本生成器，变成经过不同训练、拥有不同能力边界的工程角色。

到那时，我们谈的可能不再是一个模型多会写代码，而是一整套模型化研发系统：

- 架构模型负责系统判断；
- 开发模型负责具体实现；
- 测试模型负责寻找反证；
- 运维模型负责稳定运行；
- Agent 负责协作与治理；
- 人类负责方向、责任和最终取舍。

**让架构做架构，让开发做开发，让测试做测试，让运维做运维。**

这句话真正吸引我的，不是它听起来像一个全自动研发团队，而是它指向了一种新的工程分工：**不仅代码组件可以复用，能力本身也可以被训练、评估、版本化，并以模型的形式参与组织协作。**

如果这条路线成立，企业级 AI 编程的变化就不只是“代码写得更快”，而是研发能力开始以另一种方式被生产和组织。
