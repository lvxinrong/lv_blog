## 第二章 词元和嵌入

关于BPE 假设subagent被BPE拆分成了sub和agent两个token。但是模型如果要输出subagent 就需要返回两个sub和agent的token id。但是在解码的时候，是逐个token id解码的，那什么时候才会把sub和agent拼接起来呢？

> 假设词表中没有完整的 subagent，只有 sub 和 agent，模型会依次输出这两个 token id。由于这两个 token 本身都不含空格，解码时先分别查表得到 b"sub" 和 b"agent"，再按顺序拼接成 b"subagent"，最后做 UTF-8 解码，就得到 subagent。
> 
> BPE 的 merge 发生在 tokenizer 训练和文本编码阶段；解码阶段只做查表与拼接，不重新执行 merge。 空格、换行和标点也包含在 token 中，由模型按上下文预测，不由解码器额外添加。


在阅读完第二章中关于分词器的介绍，分别介绍了2018年的WordPiece(大小写不敏感) WordPiece（大小写敏感）。 bpe 2019年，flan-t5 2022年， gpt4的bpe 2023年， StarCoder2 2024年，Galactica 等多种分词器

> 阅读这些分词器的发展后，我的理解是：分词器首先要把连续文本转换为离散的 token id 序列，但它们关注的问题并不止于“怎样准确地切分词语”。
> 
> 随着模型任务越来越丰富，tokenizer 还需要在 token 序列中表达文档边界、片段位置、代码缩进以及其他结构信息。因此，一方面通过 BPE 等算法合并高频文本片段，提高编码效率；另一方面通过人为定义的特殊词元，为开始、结束、中间补全等结构提供明确标记。
> 
> 我感觉这是一种从“词汇级切分”走向“序列级表达”的演进：tokenizer 不只是把一句话拆成若干 token，也在帮助模型组织一整段文本及其上下文结构。不过，特殊词元本身只是协议，模型是否理解这种协议，仍然取决于后续训练。
> 
> 分词器不只是把文本切碎给模型看，也在把文本的结构告诉模型，让模型能够结合更完整的上下文理解每个 token。
> 
> 所以特殊领域是可以建立更多的特殊词元，让模型拥有更多的表达能力，比如生物，医药，化学等符号领域，领域词表负责把专业内容表达好，领域训练负责让模型真正学会这些内容。
> 
> 比如python的缩进符，擅长代码的模型大概率会把首部缩进4个空格看成一个整体处理，而不是独立的四个空格拼接，高频领域格式会被 tokenizer 压缩成整体 token，模型再通过训练学习这些 token 的结构意义。


关于文本嵌入 书中提到了词元嵌入是LLM运作的关键，但许多LLM应用需要处理完整的句子，段落甚至文本文档，催生了一些特殊的语言模型，能够生成文本嵌入-用单个词向量表示长度超过一个词元的文本片段

> 词元嵌入解决的是如何表示局部单元，句子或文档嵌入进一步解决如何表示整体语义。它让计算机可以比较两段文本“意思是否相近”，而不仅是比较它们用了哪些相同词元。至于这种整体表示是否真的保留了语义规律，而不是只记住表面文本，则取决于训练方式和评估。
> 
> 个人理解，随着模型能力增强，它不必只理解孤立的词元，而可以在上下文中理解词元组合后的整体语义。未来的优化方向不一定是让 token 无限变大，而是在保留组合能力的同时，更高效地表达文本结构。在特定领域或高频固定表达中，将完整短语甚至短句映射为单个 token id，也可能成为一种提高压缩率的探索。但 token 越大，并不意味着表达能力必然越强，还需要权衡词表规模、组合能力和对未见文本的泛化。
