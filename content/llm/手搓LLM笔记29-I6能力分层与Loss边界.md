这篇承接 [笔记 28：I6 领域后训练起步](/llm/llm-28-i6-java-defect-repair/)。

笔记 28 记录了完整方法、结构化局部编辑、8 / 16 / 32 样本学习曲线、rank 对照和 Time 最终验收。今天本来准备继续实现 span ID，结果在给定位置诊断中先撞见了一个更基础的问题：

> 我到底是在验证修复能力，还是在验证模型能否遵守一种新的输出协议？

这个问题迫使我重新思考 loss、能力分层和训练顺序。

## 一、今天真正重新理解的事：loss 不是通用能力分数

我过去谈 loss 下降时，视角还停留在一次“完整的后训练”上，容易把它当成这次训练整体效果的概括。

今天我突然意识到：**后训练的 loss 只针对当前训练集、validation 和训练目标。** 它不是模型整体能力的成绩单。

我们当前的 loss 衡量的是：

> 对当前这些“根据 buggy 方法和触发测试，生成结构化局部编辑”的样本，模型预测目标 token 的误差有多大。

它并不直接衡量：

- 通用对话能力；
- 所有 Java 编程能力；
- 所有项目的缺陷修复能力；
- 任意新指令的遵循能力；
- 编译和触发测试是否通过。

即使 validation loss 下降，也只能在当前数据分布和输出目标内解释。换一个项目、换一种输出协议，模型完全可能表现出不同的能力层次。

## 二、基础模型、adapter 与领域专门化

今天复盘时，我还明确了一个看似简单、实际很容易混淆的事实：实验里的 original 和 adapter 不是同一份模型状态。

```text
original：
Qwen3-0.6B 基础权重

adapter：
Qwen3-0.6B 基础权重
+ 8 个缺陷修复样本训练出的 LoRA adapter
```

今天使用的 adapter 是：

```text
data/model_pth/qwen3/i6-structured-08-r8-e32-c4096-best.pth
```

对应配置为：

```text
rank = 8
alpha = 16
epochs = 32
best step = 45
context = 4096
```

LoRA 训练时基础权重被冻结，学习的是额外的低秩更新。加载 adapter 后，模型行为发生变化；不加载时，就回到基础模型。

这意味着同一个基础模型可以面向不同领域或任务训练不同 adapter：

```text
Qwen3-0.6B 基础模型
├── Java 缺陷修复 adapter
├── SQL 生成 adapter
├── 内部 API adapter
└── 其他领域 / 任务 adapter
```

但每个 adapter 都只能在各自的数据、任务和评估边界内解释。不同 adapter 也不能默认简单相加就会自动获得所有能力。

## 三、能力不是一整块，可以拆成不同层次

今天的实验让我越来越清楚地看到，所谓“会修复 Java 缺陷”并不是一个不可拆分的整体能力。

至少可以分成：

| 层次 | 需要的能力 | 可以使用的指标 |
| --- | --- | --- |
| 输出契约 | 按要求生成 JSON 或指定代码结构 | valid JSON、合法字段、正常结束 |
| 定位 | 找到正确方法、连续片段或具体行 | 方法准确率、span 命中率 |
| 原文引用 | 精确复制并唯一确定待替换源码 | match_count、ready_to_apply |
| 修复内容 | 生成语义正确的替换代码 | 给定位置后的编译与触发测试 |
| 端到端修复 | 在没有人工给位置时完成完整闭环 | 未见缺陷 / 项目的 Pass@1 |

这些层次有关联，但不能互相替代。

例如 `ready_to_apply` 从 0/4 提高到 4/4，只能证明结构化输出和原文引用改善，不能证明修复内容正确。反过来，修复内容正确但 JSON 不合法，也无法进入可执行评估。

## 四、给定位置诊断：先消除定位这个变量

为了区分定位和修复内容，今天设计了 I6-GL1。

诊断样本为：

```text
Lang-10
Lang-26
Lang-28
Math-2
```

它们曾参与 checkpoint 选择，因此今天只作为开发诊断，不是新的 held-out。

模型两臂为：

```text
原始 Qwen3-0.6B
vs
8 样本、rank 8、step-45 best adapter
```

本轮由私密参考 Patch 提取正确的 `old_text`。模型可以看到 buggy 方法、触发测试和正确待替换原文，但不能看到参考 `new_text`、完整参考 Patch 或 fixed 源码。

### 评估链路先通过正控

在运行模型之前，四道参考修复均通过同一套唯一替换、编译和触发测试：

```text
reference control：4/4 编译通过
reference control：4/4 触发测试通过
```

因此后续失败不能归因于 case 或评估器已经坏掉。

### A/B 共用实际 input_ids

每题只渲染和分词一次，原始模型与 adapter 使用同一份 input_ids，并记录 SHA-256。两边重新加载底座，KV Cache 从空开始，唯一差异是是否加载 adapter。

输出预算为 512 tokens，四题最终 prompt 加输出预算的最大值只有 982 tokens，不存在 context 截断压力。

模型输出只删除末尾实际命中的 EOS，不做 `.strip()`，不按字符串切割终止标记，也不自动修复括号、反斜杠或代码围栏。JSON 序列化后还要求读回的 `new_text` 与模型原始响应完全一致。

## 五、GL1：给定位置后仍然没有成功修复

GL1 要求模型只输出用于替换 `old_text` 的 Java 代码片段。

结果为：

| 模型 | 编译通过 | 触发测试通过 |
| --- | ---: | ---: |
| 原始模型 | 1/4 | 0/4 |
| rank-8 adapter | 0/4 | 0/4 |

八个候选中，七个编译失败，一个编译成功但触发测试失败。

主要表现不是简单的“找不到 old_text”，因为 old_text 已经给定；而是模型频繁输出完整方法甚至完整类：

- Lang-10 输出完整 `escapeRegex`，而且仍保留原缺陷；
- Lang-26 的原始模型输出完整方法，adapter 输出完整类；
- Lang-28 的 adapter 输出完整 `translate`；
- Math-2 两个模型都重复未修复的完整方法。

将这些完整声明直接替换进原方法的一小段位置，通常会产生嵌套方法或嵌套类，编译失败是预期结果。

原始模型在 Lang-28 上虽然生成了可编译候选，但只是重新解析实体值，没有正确输出补充平面字符，触发测试仍失败。

所以 GL1 只能证明：

> 在给定正确位置和当前原始代码输出协议下，这八次生成都没有修复成功。

它不能直接证明模型完全没有修复内容能力，因为“只输出替换片段”的协议遵循失败已经混杂在结果里。

## 六、GL2：加强 Prompt 后，协议问题反而更明显

GL2 只改变输出提示，明确禁止完整类和方法声明，并加入一个与四道缺陷无关的玩具示例：

```text
待替换原文：int value = 1;
正确输出：int value = 2;
```

其他条件保持不变：相同四题、相同 old_text、相同两个模型、相同 512 tokens、相同贪心和原始响应保留。

结果为：

```text
原始模型：0/4 编译通过，0/4 触发通过
adapter：0/4 编译通过，0/4 触发通过
```

GL2 中：

- 原始模型在 Lang-10、Lang-26 直接复制 `int value = 2;`；
- adapter 多次复制 `[待替换原文]`、`替换后：` 等提示标签；
- Math-2 没有修复溢出公式；
- Lang-28 仍未生成正确修复。

因此不再继续调整 Prompt。GL1 / GL2 已经足够说明：**在 0.6B 上，替换片段协议本身会显著干扰修复内容诊断。** 继续调 Prompt 直到碰巧通过，不能带来干净结论。

## 七、这与昨天“指令遵循提高”并不矛盾

昨天 Time 上的真实结果是：

```text
原始模型：0/4 ready_to_apply
训练后：4/4 ready_to_apply
```

当时验证的是训练过的固定四字段 JSON 契约：

```json
{
  "action": "replace",
  "target_method": "...",
  "old_text": "...",
  "new_text": "..."
}
```

它证明了特定结构化输出和原文引用能力的改善，不是通用指令遵循能力的提升。

今天换成了一个新的协议：

```text
给定 old_text
不要 JSON
不要 old_text
不要完整方法或类
只输出 Java 替换片段
```

旧契约学习没有自动迁移到新协议，恰好说明：

> 学会一种格式，不等于理解一类任务；特定指令遵循改善，也不等于通用指令遵循能力增强。

以后记录能力结论时，必须把“哪一种指令、哪一种协议、哪一组数据”写清楚。

## 八、span 滑动窗口：候选覆盖成立，但实验推进曾经跳步

在给定位置诊断之后，我一度直接进入了候选 span 构造。

候选完全由 buggy 源码生成，参考 Patch 只用于私密侧覆盖检查。使用连续滑动窗口，结果为：

| 最大窗口 | 覆盖情况 | 候选规模问题 |
| --- | --- | --- |
| 1 行 | 3/4：Lang-26、28、Math-2 | Lang-10 的 11 行修复未覆盖 |
| 2 / 4 / 8 行 | 仍为 3/4 | Lang-10 仍未覆盖 |
| 16 行 | 4/4 全覆盖 | Lang-10 有 536 个候选，Lang-28 有 408 个 |

这说明连续 span 可以表达参考修复，但候选覆盖不是模型选择准确率，直接把数百个候选交给模型也不现实。

更重要的是，我意识到自己在这里跳步了：早上的目标是先找问题，候选构造只是一个技术分支，不能代替诊断结论。

因此 SPAN-L1 单行选择尚未运行，先暂停实现，重新整理问题。

## 九、能力可以分层，评估也可以分层

今天形成的另一个重要想法是：

> **能力是可以分层的；评估能分层，训练就可以尝试串行。**

这里的“串行”不是已经验证有效的训练结论，而是一种有前提的实验设计思路。

例如可以尝试：

```text
第一阶段：输出契约训练
验收：JSON 合法、字段完整、正常结束

第二阶段：定位训练
验收：候选覆盖、正确 span、正确方法

第三阶段：修复内容训练
验收：给定位置后的编译与触发测试

第四阶段：端到端联合训练
验收：未见缺陷和未见项目的完整 Pass@1
```

如果每个层次都有独立数据、独立指标和独立对照，就可以把“模型没修好”进一步拆成“哪一层没有学会”，而不是只看一个总 loss。

### 串行训练必须附带回归验收

分层不代表后一阶段可以破坏前一阶段。每次新增训练后，都需要重新检查：

- 旧输出契约是否仍然遵守；
- 旧验证集是否出现退化；
- 基础模型原有能力是否受损；
- 新能力是否只在训练格式中成立；
- 未见项目上的真实执行结果是否改善。

LoRA adapter 也不能默认串联或合并就一定保留所有能力。是否需要分阶段训练、共享 adapter、切换 adapter 或其他组织方式，都必须由实验回答。

所以更准确的说法是：

> **如果能力可以分层，评估也能够分层，那么就值得尝试串行训练；每一步都必须有独立验收和旧能力回归，不能只凭 loss 决定进入下一阶段。**

## 十、GL3-FM：兼容完整方法以后，修复内容仍然没有通过

为排除片段协议的干扰，GL3-FM 仍给定正确 old_text，但允许模型输出完整修复方法，并使用新的严格应用器逐字替换整个方法。

应用器不再对响应 `.strip()`，也不再用朴素花括号计数定位原方法。它校验签名、忽略字符串和注释中的花括号、拒绝额外 helper，并确认方法之外的字节不变。

四题正控均验证了：

```text
buggy 原版编译成功，测试实际执行且失败
参考完整方法逐字插入，方法外内容不变
参考修复未超出给定 old_text
修复后测试执行并通过
最终 4/4 fail-to-pass
```

模型结果为：

| 模型 | 严格合法方法 | 编译通过 | 触发测试通过 |
| --- | ---: | ---: | ---: |
| 原始模型 | 4/4 | 3/4 | 0/4 |
| rank-8 adapter | 3/4 | 3/4 | 0/4 |

原始 Lang-10、Lang-26、Math-2 和 adapter Lang-26、Lang-28、Math-2 都能编译并真实运行测试，但全部失败。多数候选只是格式变化，没有实现 Locale、整数溢出或补充平面字符修复。

因此，在当前四道开发题和当前输入信息下，可以更有把握地说：

> **即使给定正确位置，并使用兼容的完整方法协议，模型仍未生成正确修复。修复内容和缺陷理解本身已经成为明确瓶颈。**

GL1 / GL2 / GL3-FM 到此结束，不再继续调整 Prompt。I6 的目标仍未实现。

## 十一、第一性原理复盘：不要把增加上下文当成默认答案

下午重新讨论时，我意识到一个容易被混淆的问题：上下文容量和有效信息利用不是一回事。

今天 GL3-FM 四题的 prompt 加 512 输出预算最大只有 1005 tokens，并没有物理吃满 4096；但早期完整训练样本最高达到过 3413 tokens。更重要的是，即使窗口放得下，也不能保证模型能利用这些信息。输入越多，还可能越干扰。

所以这里需要区分：

```text
物理窗口是否放得下
有效信息是否足够
模型是否能利用信息
当前任务是否本来就适合单轮生成
```

盲目增加源码、日志和测试历史，不一定能解决修复内容问题。

## 十二、从一次性答案到有限轮次的真实反馈

当前所有单轮实验都要求模型一次性给出正确答案。这相当于不允许它动手修改、运行编译器、读取异常栈和执行单测。

但真实程序修复通常是一个闭环：

```text
观察行为偏差
→ 提出缺陷假设
→ 做最小修改
→ 编译 / 测试
→ 根据真实反馈修正假设
→ 再验证
```

因此，多轮反馈不是简单多抽几次答案。无反馈重复生成只是 Pass@k；带反馈的多轮则会在每一轮获得新的真实信息。

当前设想为：

```text
模型输出完整候选方法
→ harness 严格校验并替换
→ harness 调用编译器和 Defects4J
→ harness 提取最小失败信息
→ 模型根据当前方法 + 反馈生成下一版
```

第一版不让模型自己决定工具调用协议，先由 harness 管理工具。这样可以把“是否会利用反馈”和“是否会调用工具”分开，避免新增 JSON 工具协议再次成为混杂变量。

### 多轮不等于无限累积历史

每轮只保留一个外部状态：

```text
当前候选方法
当前编译错误或失败断言
相关测试与源码
当前轮次
```

完整日志保存在文件中，模型只接收预定义的最小失败反馈。这样上下文不会随轮次无限增长。

拟议中的实验暂记为 `repair-loop@3`：

- 沿用 GL3-FM 的八个候选作为第 0 轮；
- 原始模型与 rank-8 adapter 保持对照；
- 最多修订 3 轮；
- malformed、compile_failed、trigger_test_failed 分别反馈；
- 测试通过立即停止；
- 输出完全不变记为 no_progress；
- 三轮仍未通过记为 budget_exhausted；
- 不与原来的 Pass@1 混算，不使用 Time 调参。

该闭环目前只是实验方向，尚未实现和验收。

## 十三、多轮 Agent 与微调初衷的边界

我同时意识到：训练一个更会修复的 0.6B 模型，与用 0.6B 为核心搭一套修复 Agent，是两个相关但不同的目标。

如果把 Agent 的系统结果直接写成“后训练让模型学会了修复”，就会夸大训练结论。

因此后续报告需要区分：

```text
I6-M：模型本身的领域后训练能力
I6-A：同一 0.6B 在工具闭环中的系统修复能力
```

微调是否仍然有意义，取决于训练目标：

- `buggy 方法 → 最终修复`，训练的是直接修复；
- `当前候选 + 编译 / 测试反馈 → 下一版候选`，训练的是反馈修正。

多轮闭环并不天然否定微调，但它改变了模型需要学习的能力。两种结果可以互相解释，不能混为同一个成功指标。

## 十四、先降低难度：给 Defects4J 官方案例分层

另一个方向是承认当前缺陷对 0.6B 的单轮生成可能过难，但不用“难 / 不难”一概而论。

当前 validation 本身就混合了多种难点：

- Math-2：整数乘法溢出与精度；
- Lang-28：Unicode 补充平面字符；
- Lang-26：Locale 上下文；
- Lang-10：连续多行删除；
- 另外还叠加了方法长度、输出协议和测试信息不足。

可以优先从 Defects4J 官方案例中筛选局部修复：

- 单文件、单方法、单 hunk；
- 参考修复只需修改局部方法；
- 不新增字段、helper、import 或跨文件修改；
- buggy 原版可编译、测试失败，局部参考修复后通过；
- 不需要大量仓库上下文。

拟议中的难度层为：

```text
D1：单行、单 hunk、短方法、明确局部语义
D2：单行修复，但需要数值 / Unicode / Locale 等领域知识
D3：多行或跨多个相关代码块
D4：需要类字段、其他方法或仓库上下文
D5：多方法、多文件修复
```

Defects4J 保留为真实缺陷评估场，但不一定适合作为 0.6B 的起步课程。局部变异缺陷可以用于 D1 教学与诊断，再用真实 Defects4J 检查迁移。

难度分层尚未执行，不能只凭当前 0/4 就断言整个 Defects4J 对 0.6B 太难。

## 十七、重要发现：4B 没有修错，而是四题都直接复制了 buggy 方法

Qwen3-4B 官方权重已经在 Mac 和 Windows 上完成 V4 加载与生成冒烟。正式四题对照使用相同 input IDs、相同 bf16、相同完整方法 Prompt、相同贪心 Pass@1 和同一严格完整方法应用器，不加载任何 LoRA。

结果为：

| 模型 | 修改了方法 | 编译通过 | 触发测试通过 |
| --- | ---: | ---: | ---: |
| 0.6B bf16 | 4/4，但主要是格式变化 | 3/4 | 0/4 |
| 4B bf16 | 0/4 | 4/4 | 0/4 |

4B 四题都满足：

```text
method_changed = false
changes_outside_given_old_text = false
compile_returncode = 0
trigger_test_passed = false
```

这意味着 4B 没有提出错误修复，而是**四题都逐字返回了 buggy 方法**。它只是复述了输入，没有实际尝试修改代码。

因此，模型规模增大在当前协议下没有产生修复收益。不能据此推断 4B 修不了所有 Defects4J，也不能把规模永久排除；只能说在相同任务表达和 Pass@1 下，0.6B 与 4B 都没有成功。

### Prompt 成为新的强嫌疑

如果 4B 给出了看似合理但测试失败的修改，我会更倾向于任务语义或模型能力不足。但四题逐字复制说明，当前 Prompt 可能一直在诱导“复述完整方法”，而不是“根据行为偏差修改方法”。

当前输入可能存在以下问题：

1. 只有测试源码，没有真实失败断言、异常栈和 expected / actual，模型未必知道该改变什么行为；
2. 输出契约文字占比很高，模型可能把任务理解成按格式复述方法；
3. 完整 buggy 方法被完整放在输入中，复制输入成为语言模型的一条低阻力路径；
4. 两个模型都关闭了 thinking，当前对照没有覆盖官方推理模式是否会影响修复。

所以，**我现在怀疑问题可能出在提示词和任务表达上，而不是单纯出在模型规模上。**

这仍然只是有证据支持的假设，不是已经证实的 Prompt bug。下一步应先审查当前完整 Prompt，并设计一个只改变任务表达的固定对照：

```text
明确方法包含已知缺陷
提供真实失败断言 / 异常 / expected / actual
要求根据行为偏差修改代码，而不是复述方法
继续输出严格完整目标方法
```

如果提供真实失败信息后模型才开始修改，说明之前缺的是有效任务信息；如果仍然复制，才需要继续检查推理模式、修复内容能力和基座限制。

当前行动顺序因此调整为：

```text
先审查 Prompt 的复制倾向与缺失信息
→ 再做局部 Defects4J 难度分层
→ 在相同任务上比较单轮与有限轮次反馈
→ 最后决定后训练目标是直接修复还是反馈修正
```

不继续扩大模型规模，不继续调整 rank，SPAN-L1 继续暂停。Time 不参与这些开发诊断。

## 十八、四题横向红队与去重复对照：行为改变不等于修复收益

四题 Prompt 的横向审查进一步收紧了假设：它们共享一个值得验证的复制诱因，但信息缺口并不相同。

共同结构是：old_text 都能在 buggy 方法中唯一匹配，却又被逐字放在 User 段最后。完整 buggy 方法本身已经满足签名、花括号和无包装等输出要求，因此模型可以交付形式合法但行为未变的方法。

信息缺口则因题而异：

- Lang-10 的判定藏在外层测试调用的 helper 中；
- Math-2 通过采样间接暴露问题；
- Lang-26 已给出预期格式，但缺实际输出；
- Lang-28 已给出较具体的实体输入、预期 UTF-16 序列和断言。

因此不能再说四题都只是缺上下文。

### 去重复对照的唯一改动

四题统一将尾部逐字 old_text 换成方法内行号：

```text
Lang-10：第 2–12 行
Lang-26：第 2 行
Lang-28：第 29 行
Math-2：第 2 行
```

完整 buggy 方法、测试文本、System、Qwen 标记、空 think 块、输出契约和生成预算均保持不变。使用 4B 官方权重、bf16、无 adapter、thinking=False、贪心单轮 Pass@1。

结果为：

| 实例 | 原 4B 基线 | 去重复后 | 编译 | 触发测试 |
| --- | --- | --- | --- | --- |
| Lang-10 | 逐字复制 | 仍然逐字复制 | 通过 | 失败 |
| Lang-26 | 逐字复制 | 产生修改 | 通过 | 失败 |
| Lang-28 | 逐字复制 | 产生修改 | 通过 | 失败 |
| Math-2 | 逐字复制 | 产生修改 | 通过 | 失败 |

去重复改变了三题的输出行为，但没有让任何题通过触发测试。它只能支持“定位表达变化影响了输出行为”，不能证明尾部重复是修复失败的根因。

另外，三题的 `changes_outside_given_old_text=true`，说明这些变化属于整方法编辑，不能据此声称局部片段协议已经成功。

本轮结束后停止继续调整 Prompt。

## 十九、Math-2 行为证据：实测矛盾仍然没有被利用

原 Defects4J 测试输出只有失败测试名称，没有实际断言值或异常栈。不能把静态推算直接填进 actual。

因此为 Math-2 增加了一个独立探针：在 buggy 工作区、使用与触发测试相同的构造参数，通过 Java 11 `jshell` 直接调用 `getNumericalMean()`。

真实记录为：

```text
BUGGY_MEAN_PROBE = -49.759350398538686
EXPECTED_BY_DISTRIBUTION_DEFINITION = 49.821236993679285
```

其中：

- 第一项是 buggy 工作区中目标方法的真实探针测量；
- 第二项按超几何分布定义 `n * (m / N)` 独立计算；
- 它不是原 sample() 测试的 actual 字段。

随后在行号定位版 Prompt 中，只增加这两个实测值和上述探针边界，不提供溢出解释、类型转换建议或参考修复。

结果仍然是：

```text
method_changed = false
changes_outside_given_old_text = false
compile_returncode = 0
trigger_test_passed = false
```

也就是说，4B 在看到实际负均值和独立正期望值后，仍逐字复制了 buggy 方法。

这只能证明：**在当前 4B、bf16、thinking=False、贪心单轮条件下，仅增加这一条真实行为证据仍然不够。** 不能推广为行为证据对所有模型或其他任务都无效。

## 二十、thinking 对照：推理过程没有收敛

最后一个独立变量是 `enable_thinking`。

两种模式都使用 2048 输出 tokens，保持 Math-2、4B、bf16、行号定位和实测行为证据不变。thinking off / on 的 input IDs 差异来自模板分支，用户任务文本保持一致。

### thinking-off

模型再次逐字复制 buggy 方法：

```text
method_changed = false
finish_reason = stop
compile_returncode = 0
trigger_test_passed = false
```

### thinking-on

模型生成了 2048 tokens，但没有发出 EOS，也没有关闭 `</think>`：

```text
finish_reason = length
think close count = 0
evaluation_status = length_limited
没有形成候选方法，未进入编译和测试
```

原始推理文本显示，模型反复猜测 getter 是否对应错误参数，并反复复述“为什么正数计算会得到负数”。

它已经写出了：

```text
50 × 42,976,365 = 2,148,818,250
```

却没有在这 2048 tokens 内把它与：

```text
Integer.MAX_VALUE = 2,147,483,647
```

联系起来，也没有定位到“int 乘法先于 double 转换发生溢出”。

因此，开启 thinking 没有解决 Math-2，反而暴露出推理过程反复假设、自我否定但不收敛的问题。继续增加预算没有当前证据支持，本轮停止。

## 二十二、Lang-33：连“数组中的 null 元素”也没有修好

最终选中的真实局部案例是 Lang-33。

Buggy 方法在转换对象数组时直接调用：

```java
classes[i] = array[i].getClass();
```

测试明确包含一个 null 元素，并期望它被映射为 null：

```java
new Object[] { "Test", null, 99d }
→ String.class, null, Double.class
```

参考修复只需要一行：

```java
classes[i] = array[i] == null ? null : array[i].getClass();
```

它是单方法、单行修改，测试直接调用目标方法并明确给出期望行为，不需要仓库全局视野。相比数值溢出、Unicode 和 Locale 题目，这被当作当前最接近 D1 的真实缺陷起点。

### 参考正控与结构化端到端结果

参考结构化 edit 经唯一替换后，编译和触发测试均通过，说明案例与评估链路有效。

原始 0.6B 虽然生成了合法 JSON 和唯一匹配，但 old_text 是方法签名，new_text 则是一整个仍保留旧逻辑的方法。将完整方法塞进方法签名位置后，编译失败。

当前 8 样本 rank-8 adapter 则生成了源码中不存在的 `return classes[i];`，并引入无关的 `getDeclaredClass()`，最终为 `match_not_found`，没有进入编译测试。

结构化端到端结果因此为：

```text
原始模型：compile_failed
adapter：match_not_found
真实修复通过：0
```

### 完整方法协议复测

为区分片段协议与修复内容，又使用 GL3-FM 完整方法协议，以行号给出位置，分别测试 0.6B 与 4B 官方权重、bf16、无 adapter。

两个模型都生成严格合法的完整方法，都能编译并真实运行测试，但都没有加入 null 条件：

```java
for (int i = 0; i < array.length; i++) {
    classes[i] = array[i].getClass();
}
```

最终结果为：

| 模型 | 方法结构合法 | 编译通过 | 触发测试通过 |
| --- | ---: | ---: | ---: |
| 0.6B | 1/1 | 1/1 | 0/1 |
| 4B | 1/1 | 1/1 | 0/1 |

`method_changed=true` 仍只是缩进和格式变化，不是语义修复。`changes_outside_given_old_text=true` 也表明这些属于整方法变化，不能包装成局部修复能力。

Lang-33 到此完整收尾。它留下的不是一个悬而未决的候选，而是一条清楚的负结果：**连一个测试明确、只需处理 null 元素的单行真实修复，当前两组模型都没有完成。**

## 二十三、真正未被验证的前置假设：我们默认 0.6B 会 Java

回看 I6 的整个过程，我一直带着一个潜意识假设：

> **0.6B 既然是大语言模型，又读得出 Java 代码，那么它应该已经会 Java，只需要通过后训练学会缺陷修复。**

但这个假设从未被系统验证。

模型能复述方法、生成合法 JSON、保持方法签名，甚至输出一个可编译的方法，都不能证明它掌握了足够的 Java 语法、类型、边界和基本逻辑语义。

Lang-33 与 Math-2 进一步说明，问题可能不只是“领域后训练不够”，而是我对模型现有基础能力的判断本身就缺乏证据。

因此，评估顺序必须继续前移：

```text
不是先问：模型会不会修复真实缺陷？
而是先问：模型到底会不会写最基本的 Java？
```

如果连明确规格下的短方法都无法稳定编译和通过独立断言，就应当承认当前模型与协议还没有足够的写实代码 Java 表征，先暂停讨论更高阶的缺陷修复，而不是继续用 loss 或格式成功掩盖这个缺口。

这不是宣判模型永远没有价值，而是拒绝继续建立在一个未经验证的能力假设上。

## 二十四、今日收官：后续冻结为四步能力评估

后续不再从 Defects4J 的真实修复率直接倒推模型能力，而是按以下顺序逐层评估。

### 第一步：Java 语法与常识

给模型明确的空方法签名或规格，例如：

- 返回两个数之和；
- 返回数组最大值；
- 遍历数组并求和；
- 字符串转大写，null 输入返回 null；
- 返回两个 int 相除的 double 结果；
- 处理数组索引、边界和基本异常。

验收不是“看起来像 Java”，而是：

```text
严格方法结构校验
→ javac 编译
→ java -ea 独立断言运行
```

这一步先使用原始 0.6B，不加载 adapter，固定贪心 Pass@1。参考实现先通过同一应用器正控。

### 第二步：人工构造 20 道单行 D1 修复题

只涉及短方法和单行 bug，按基础逻辑类别拆分：

```text
数组越界
off-by-one
null 元素
错误比较符
错误返回值
int / double 类型转换
整数溢出
条件写反
循环边界错误
```

每题都需要明确规格、直接测试和参考修复，不能把仓库级知识偷偷混进“简单题”。

这一步回答：模型在会基本 Java 的前提下，是否具备最简单的局部逻辑修复能力。

### 第三步：回到真实 Defects4J 局部案例

只选单文件、单方法、单 hunk、极少行修改、测试直接调用目标方法的实例。

Lang-33 保留为这一层的已知失败基线，而不是从评估集中消失。后续可以用它检查新训练或新协议是否真正带来“失败 → 通过”。

### 第四步：Defects4J D2 / D3

最后才逐步增加：

- 数值、Unicode、Locale、时区等领域语义；
- 多行和多个相关代码块；
- 类字段、helper 和更多仓库上下文；
- 更真实的跨方法、跨文件修复。

这一步才用于描述 0.6B 的能力边界，而不是一开始就把所有难度混在一起。

### 评估与训练的边界

四步都先做基础模型能力画像，再比较 adapter，必要时才引入同口径的 4B 对照。不能因为某个 adapter 在训练格式中表现更好，就省略基础能力评估。

有限轮次反馈、工具调用和 Agent 闭环继续作为系统能力对照，不能与纯模型单轮修复混算。SPAN-L1 继续暂停，直到定位被重新证明是当前主要瓶颈。

如果后续能力评估表明某一层确实薄弱，再针对该层设计串行训练，并对旧能力做回归。这样“能力分层、评估分层、训练串行”才有可执行的基础。

## 二十五、今天笔记收官，但 I6 没有完成

今天没有得到一个通过的真实修复，但终于把问题从“再试一次训练”推进到了“先验证模型到底会什么”。

今天真正沉淀下来的是：

- loss 只描述当前数据和训练目标，不是通用能力分数；
- 特定 JSON 契约的改善不等于通用指令遵循；
- 结构合法、可应用、编译通过和触发测试通过是不同层次；
- 样本量、rank、模型规模、Prompt、行为证据和 thinking 都不能被当成无需验证的万能旋钮；
- 多模型红队可以暴露假设漏洞，但真实执行结果负责裁决；
- 最基础的能力假设也必须被实验验证。

**今天的笔记在这里收官。I6 仍未完成，下一次从 Java 语法与常识评估开始。**

> **loss 是局部探针，不是通用能力证明。能力可以分层，评估可以分层，训练才有条件被拆成可归因、可回归、可复核的阶段。**
