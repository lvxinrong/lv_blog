有一个场景，至今仍然很能说明这三天的实验。

Defects4J 中的 Lang-33 只需要处理数组里的 `null` 元素。测试直接告诉模型：输入中包含一个 `null`，期望输出中对应的位置也保留 `null`。参考修复只需要在调用 `getClass()` 前增加一次空值判断。

这是一个单行修改，不需要理解整个仓库，也不需要复杂的架构知识。

但 0.6B 没有修好，4B 也没有修好。

真正让我停下来反思的，不是“又大又小两个模型都失败了”，而是另一个问题：

> 我一直在尝试通过微调让模型学会修复，却从来没有系统验证过，它是否真的具备支撑修复工作的 Java 基础能力。

这篇文章记录的就是这个问题如何一步步浮现出来。它不是一篇成功教程，也不是“0.6B 学不会 Java”的判决书，而是一次从真实缺陷修复出发，不断提出假设、验证、否定假设，再把问题继续往前推的实验复盘。

## 一、第一天：先确定什么叫“修复成功”

I6 最初的目标很明确：Java 缺陷定位与最小修复。

我选择 Defects4J 作为第一块训练与验证场地。它提供真实 Java 项目的 buggy / fixed 版本，更重要的是提供触发测试：同一个测试在 buggy 版本上失败，在 fixed 版本上通过。

这意味着模型是否正确，不必由另一个模型凭文字风格来评判，而可以由编译器和测试直接回答：

```text
定位正确
→ 补丁能够应用
→ 项目编译成功
→ 触发测试从失败变为通过
→ 相关回归测试保持通过
```

为了控制变量，第一版评估固定为相同提示词、贪心生成、单次生成不重试。不同失败也分别记录：输出为空、格式非法、补丁无法应用、编译失败、触发测试失败，而不是全部写成“模型没修好”。

现在回头看，这是整三天里最重要的一步。因为后面许多看似矛盾的结果，最后都要回到同一个问题：**到底是哪一个环节没有通过？**

## 二、完整方法训练：真正的修复被复制 token 稀释了

最初的训练方式，是让模型阅读 buggy 方法和触发测试，再输出修复后的完整方法。

单样本实验很快出现了第一次“记忆与迁移分离”。

微调后的模型能够学会 Lang-5 的修复，并在 Defects4J 的真实编译和触发测试中通过；但把同一个微调后的模型用于 Lang-3，精度限制仍然没有补上，触发测试继续失败。

这已经说明：

```text
训练样本学会 ≠ 未见样本也会修复
```

完整方法训练还暴露了另一个问题。

Lang-16 的参考修复实际上只有一行：让十六进制前缀判断同时支持大写 `0X` 和 `-0X`。但完整修复方法有 6079 个字符、1212 个监督 token。模型绝大部分训练容量都用在复制原本就正确的方法体，真正需要学习的那一行修改，被大量复制 loss 稀释了。

所以问题不一定是“数据太少”，也可能是**输出契约让监督信号落在了错误的位置**。

于是我把输出改成结构化局部编辑：

```json
{
  "action": "replace",
  "target_method": "createNumber",
  "old_text": "需要修改的精确原文",
  "new_text": "用于替换原文的最小修复代码"
}
```

模型只负责提出修改，评估器负责检查原文是否唯一匹配、执行一次替换，再编译和运行测试。监督目标从完整方法的 1212 个 token，缩短到约 80 个 token。

这次调整再次证明，微调后的模型可以记住训练样本并生成正确替换，但未见缺陷上的修复仍然没有发生。

结构化格式学会、训练样本记住、未见缺陷会修复，是三个不同结论。

## 三、第一天的边界：可应用补丁增加，真实修复仍为零

随后我又做了样本量、训练轮数和 LoRA rank 的对照。

增加样本量和训练步数后，训练指标有所改善，但同一组验证集上的触发测试通过数仍然是 `0/4`。把 rank 从 8 增到 16，训练集拟合更强，验证集修复仍然为零，并伴随更强的过拟合。

最后在未参与训练的 Time 项目上，出现了一条很容易误读的结果：

| 指标     | 原始模型 | 微调后的模型 |
| ------ | ---: | -----: |
| 可应用补丁  |  0/4 |    4/4 |
| 编译通过   |  0/4 |    1/4 |
| 触发测试通过 |  0/4 |    0/4 |

如果只报告第一行，似乎微调带来了明显成功；但完整结果只能说明，微调后的模型在未见项目上更能遵守结构化输出要求，并精确引用原文。

它不能证明修复内容正确。

第一天结束时，我已经不得不接受：**loss 下降、输出更规范、补丁可应用，都不等于真实修复能力形成。**

## 四、第二天：到底是输出协议不对，还是修复内容不对？

第二天一开始，我准备继续做候选位置选择，但很快发现还有一个更基础的问题没有解决：之前那些失败，到底是模型不理解修复，还是模型被新的输出协议卡住了？

于是我把“定位”这个变量先拿掉，直接把正确的待替换原文提供给模型。

在只输出 Java 替换片段的协议下，模型频繁返回完整方法甚至完整类。把这些声明塞进原方法的一小段位置，通常会产生嵌套方法或嵌套类，编译自然失败。

加强提示词、加入玩具示例后，问题反而更明显：模型开始复制示例、复制提示标签，或者继续输出未修复的完整方法。

最后，我改用兼容性更好的完整方法协议，仍给定正确位置，让模型输出整个修复方法。结果大多数候选都能保持方法结构并编译，但触发测试依然全部失败。

到这一步，结论才稍微清晰了一些：

> 即使给定正确位置，并使用兼容的输出协议，修复内容和缺陷理解本身仍然是明确瓶颈。

这也让我第一次真正分清：输出契约、定位、原文引用、修复内容和端到端修复，是不同层次的能力。某一层改善，不能自动证明下一层也会改善。

## 五、4B、行为证据与 thinking：几个常见答案都没有奏效

面对修复内容失败，几个很自然的假设接踵而至。

### 1. 是不是 0.6B 太小？

我把同一批失败案例交给 Qwen3-4B 官方原始权重，保持相同提示词、数值精度、贪心生成和单次评估。

结果 4B 在四道题上都逐字返回了 buggy 方法，没有尝试修改。

它编译通过，因为复制的方法本身可以编译；但触发测试仍然失败。模型规模增大，在当前任务表达下没有带来修复收益。

### 2. 是不是提示词诱导复制？

原提示词把待替换原文逐字放在输入末尾，可能让模型误以为只要复述完整方法即可。于是我把逐字原文改成行号。

三题的输出行为确实发生变化，模型开始修改方法，但没有任何一道通过触发测试。

这只能说明提示词影响了行为，不能证明它就是修复失败的根因。

### 3. 是不是缺少真实行为证据？

针对 Math-2，我在 buggy 工作区中实际调用目标方法，得到负的平均值，再按分布定义独立计算出正期望值，把这两个真实数字提供给模型。

4B 仍然逐字复制 buggy 方法。

### 4. 开启 thinking 是否能解决？

开启 thinking 后，模型反复猜测、反复否定自己，直到耗尽输出预算，也没有关闭思考过程并形成候选方法。

它已经写出了会超过 `Integer.MAX_VALUE` 的乘法，却没有把结果与整数溢出联系起来。

这几轮实验没有给我想要的成功，却阻止我继续把“换大模型、改提示词、增加信息、开启推理”当成无需验证的通用答案。

## 六、Lang-33：真正被忽略的前置假设

随后，我筛选出更接近最小修复目标的 Lang-33。

Buggy 方法在遍历对象数组时直接执行：

```java
classes[i] = array[i].getClass();
```

测试明确包含一个 `null` 元素，期望它被映射为 `null`。参考修复只需要：

```java
classes[i] = array[i] == null ? null : array[i].getClass();
```

原始模型和微调后的模型在结构化编辑协议下都没有产生可编译的正确补丁。换成完整方法协议后，0.6B 与 4B 都能生成合法方法并编译，却都保留了原来的直接调用，没有加入 null 判断。

这时已经是第二天晚上。连续失败之后，我才真正意识到一个此前一直忽略的问题：

> 我默认了“大模型读过 Java 代码，就应该已经会 Java”，但这个假设从未被系统验证。

模型能复述方法、保持签名、生成合法 JSON，甚至输出可编译代码，都不能证明它理解类型、边界、null、整数除法和基本逻辑语义。

所以，问题需要继续前移：

```text
不是先问模型会不会修真实缺陷
而是先问模型到底会不会最基本的 Java
```

## 七、第三天：先验证 Java 基础，而不是继续修真实缺陷

第三天，我先给原始 0.6B 一组明确规格的短方法：两数相加、返回较大值、数组求和、统计偶数、处理 null 字符串、执行 double 除法。

每道题都要求严格校验方法结构，再执行 javac 和独立断言。参考实现先通过同一套链路，避免把评估器故障算到模型头上。

基础指令版最终只有 2/6 通过。继续加强完整性要求、使用 assistant prefill、改成纯文本续写或极简自然语言，都没有提高通过率，部分方式反而让输出更发散。

中间还发现过一个评估器问题：结构校验读取的是模型候选，但编译和断言阶段却写入了参考实现。修正后，原先看起来更漂亮的成绩被取消。这个插曲再次提醒我，**评估结果是否可信，首先取决于评估器到底在测谁。**

概念与代码阅读测试也暴露了类似问题：

- 把 `final` 理解成初始化后仍可重新赋值；
- 认为 `1 / 2` 会得到 `0.5`；
- 混淆 `==` 与 `equals`；
- 认为 static 方法可以直接访问实例字段；
- 没有识别 null 调用方法会抛出异常；
- 没有识别数组下标越界。

但模型也并非完全不会 Java。两数相加、两个数取较大值、部分 `String.equals` 和 overload 回答是正确的。更准确的状态是：知识点零散、表层化，无法稳定支撑精确执行。

## 八、概念 SFT：从“补基础”到三次常见假设

基于这些结果，我开始尝试用 LoRA + 监督微调（SFT）补充基础概念。

训练数据覆盖 static、final、整数除法、`== / equals`。最初 100 条中有 92 条用于训练，后来因为 static 错误集中，又补充 30 条，形成 122 条训练数据。

接下来的三个假设，几乎是最自然的反应。

### 1. 是不是训练次数不够？

4 epochs 后出现了局部概念改善，增加到 8 epochs 却没有整体超过前者，部分题目改善，另一部分回落。继续增加到 16 或 32 epochs 缺少依据。

### 2. 是不是 static 样本不够？

新增 30 个 static 场景后，问题仍然没有稳定改善。模型甚至会先说出“static 字段由所有实例共享”，紧接着又把本应为 `2 2 2` 的输出算成 `0 0 0`。

### 3. 是不是学习率太小？

我把学习率从 `1e-5` 提高到 `1e-4`，其他条件保持不变。

单看训练指标，它似乎有效：

| 指标                         | lr = 1e-5 | lr = 1e-4 |
| -------------------------- | --------: | --------: |
| final train loss           |  1.880346 |  1.150991 |
| final full validation loss |  2.064561 |  1.843811 |
| optimization steps         |       488 |       488 |

但训练原题和独立题的生成都出现了多处退化。

于是问题变成：train loss 和 validation loss 都在下降，为什么目标行为反而在变差？

继续调参不能解释这个矛盾，我需要先检查实验环境本身。

## 九、给训练管线做环境验证

### 1. 训练与评估的提示词并不一致

回查脚本后，我发现训练时使用：

```text
system = Java 教师要求
user   = 原始问题
```

旧评估却把教师要求和 `[问题]` 包装一起放进了 user，角色分配和文字包装都不同。

为排除这个变量，我增加 SFT 提示词模式，并对全部 122 条训练样本做 token 前缀校验。最终 122 条全部通过，确认训练和评估在输入契约上逐项一致，而不只是“文字看起来差不多”。

### 2. 训练是 FP32，旧生成却是 BF16

训练脚本使用 PyTorch 默认的 FP32，旧生成却显式使用 BF16。运行时核验确认，训练模型和保存下来的微调参数都是 FP32。

因此不需要为了统一精度重新训练，直接让微调后的模型以 FP32 生成即可。

FP32 确实改变了部分输出，有些题改善，有些题出现新的矛盾，但核心错误没有消失。精度会影响生成轨迹，却不是全部失败的解释。

### 3. 用 8 条样本强行过拟合

为了验证训练、保存、加载和生成这条链路是否能够完成最基本的学习，我又选出了 8 条 static 训练原题，故意加强优化，只看模型能不能背下来。

```text
训练样本：8 条
epochs：64
optimization steps：512
learning rate：1e-4
initial train loss：3.149048
final train loss：0.000205
```

随后让微调后的模型回测相同 8 题，结果是 8/8 与参考答案逐字一致。

这证明在当前概念任务上，整条链路具备明确的学习和复现能力。它不能证明泛化，但能排除“训练完全无效”“微调参数没有加载成功”“生成链路无法复现训练结果”等错误方向。

这让我联想到排查 Java 生产问题时的环境验证：先确认源码、依赖、配置、网络和目标环境，再讨论复杂业务逻辑。

模型训练也一样：

> **大模型是黑盒，但围绕它的工程管线必须尽量白盒。**

## 十、loss 与自由生成之间，还隔着什么？

接下来，我测量了高学习率模型在这 8 条训练答案上的损失。计算时使用“给定标准答案前缀”的方式，也就是每一步都把正确前缀提供给模型，而不是让模型消费自己生成的前缀。

结果 8 条样本的损失全部进一步下降，平均值从 `1.729874` 降到 `0.851884`。这排除了“平均 loss 下降是因为这 8 条被其他样本牺牲”的解释。

但它仍不能证明模型可以自主作答。

计算损失时，即使模型本来想在开头写“错误”，后续计算仍然会把正确的“正确。……”喂给它。模型可以学会在正确结论后接一段像样的话；自由生成时，它一旦先写出“错误”，后续就可能沿着错误结论继续解释。

长答案中的大量通用措辞，还会让模型越来越像参考答案，却不保证“能/不能”、`1 1/2 2`、`true/false` 等关键内容正确。

所以：

> **参考答案在教师强制条件下更容易出现，不等于模型能够在自由生成时独立给出答案。**

为了排除全序列训练与增量解码之间的工程差异，我还比较了使用和不使用键值缓存（KV cache）的生成结果。相同模型、提示词、FP32 和贪心设置下，8 道题输出逐字一致，KV cache 也被排除为主要原因。

至于“长解释是否稀释了关键结论的监督”，到这一步仍然只是一个假设。需要把结论从解释中拆出来，单独验证。

## 十一、红队审查：测试题和测试角色本身也有问题

在准备短答案实验时，我请另一个模型做了红队审查。

它首先指出，原题库中有一道 `L0-HOLDOUT-01`：类里的 `current()` 本身无法编译，却又同时询问 main 输出。参考答案中的输出值，需要先移除或修正非法方法才能实测。

这说明短答案不能简单截取长答案首句。每道题都应该重新写成单一、可执行的问题，编译标签由 javac 决定，输出标签由实际运行决定。

红队还指出，原来的 20 条“独立验证题”虽然文件里标记为 `eval_holdout`，但我已经反复根据它们的结果选择增训方向、调整提示词、调整精度和设计下一轮实验。它们更适合作为开发回归集，而不能再冒充从未参与设计决策的最终验收集。

这让我意识到：

> **测试集是否独立，不只取决于文件中的角色，还取决于它后来是否参与了设计决策。**

同时，我也开始收缩目标。Java 规范对人类来说是一小块知识，但对 0.6B 模型来说，程序及其行为的组合空间非常大。如果要求自己先“补完整套 Java”再修 bug，这条支线可能永远没有收口。

于是最后只验证一条规则：

> static 方法不能直接访问实例字段，但可以通过显式对象引用访问。

## 十二、成对验证：单题 50%，整对却是 0%

我构造了成对代码。每对的类、方法签名和其他代码保持一致，只改变访问形式，例如：

```java
class Wallet {
    int balance;

    static int peek(Wallet w) {
        return balance;
    }
}
```

与：

```java
class Wallet {
    int balance;

    static int peek(Wallet w) {
        return w.balance;
    }
}
```

第一段非法，第二段合法，标签全部由 javac 实际编译决定。

原始 0.6B 对 8 个代码片段全部回答 `合法`。旧微调模型对第一对的两个版本都回答 `非法`，其余三对的两个版本都回答 `合法`。

按单题计算，两个模型都恰好答对 4/8，看起来有 50% 准确率；按整对计算，却都是 0/4。

这证明成对验收的必要性：

> **如果合法与非法版本总得到相同答案，单题猜中不能算作掌握规则。**

自由短答案和候选答案评分给出了相同结果，也说明问题不只是输出协议，模型确实没有利用字段访问形式的变化来区分代码行为。

随后，我重新冻结了 4 对最终题和一个 `Thermostat` 单行修复题。最终集只运行 javac 验标签，不运行模型，10/10 检查通过。

## 十三、最后一次短标签训练：迁移与修复都没有发生

最后一次训练只使用 4 对开发题，共 8 条短标签样本，非法与合法各 4 条。模型从原始 0.6B 开始，不叠加旧微调结果，避免混合两种训练目标。

实际执行配置为：

```text
训练样本：8 条短标签
epochs：16
optimization steps：128
learning rate：1e-4
训练与生成：FP32
```

训练前曾讨论是否把学习率改为 `3e-5`，但实际命令仍执行为 `1e-4`，实验记录也按真实值保留。

最终训练损失从 `0.933424` 变为 `0.989837`，没有下降。使用微调后的模型评估冻结的 4 对最终题，8 个未见代码片段全部回答 `合法`：

```text
generation_correct_pairs：0/4
score_correct_pairs：0/4
generation_same_answer_pairs：4/4
score_same_answer_pairs：4/4
```

短标签训练没有让模型在未见代码上学会这条规则。

最后是 `Thermostat` 单行修复。模型需要输出一个 replace JSON，修复后还要通过 javac 和运行断言，确认 `Thermostat.read(t)` 返回传入对象的 `degrees`。

模型实际只输出了：

```text
int degrees;
```

因此没有生成符合契约、可供编译评估的补丁，不能把它写成“补丁编译失败”。

至此，事先约定的停止条件已经满足：短标签训练既没有迁移到最终成对题，也没有完成同规则微型修复。我不再继续增加 epochs、学习率、rank、数据量或新的 Java 主题。

## 十四、这三天真正留下的东西

从技术目标看，这次微调没有成功。但实验并不是只有“模型训练成功”这一种成果。

第一，问题的层次变得更清楚了：

```text
输出结构合法
原文能够唯一匹配
补丁可以应用
代码可以编译
触发测试通过
未见样本能够迁移
```

这些结果分别对应不同能力，任何一层都不能代替下一层。

第二，训练指标和行为能力被彻底分开了：

```text
loss 下降 ≠ 目标能力形成
记住答案 ≠ 会迁移规则
会判断规则 ≠ 会修复缺陷
通过测试 ≠ 一定语义正确
```

第三，我得到了一个更可靠的排查顺序：

```text
先检查数据和输入契约
→ 检查设备、精度和生成方式
→ 检查优化是否改变目标概率
→ 检查微调结果的保存与加载
→ 用最小过拟合验证记忆闭环
→ 用未见题验证迁移
→ 用编译和行为验证修复
```

低一层没有验证清楚，就不急着在更高一层增加变量。

第四，我重新理解了红队的价值。红队不是增加一个投票者，而是引入一个专门挑战前提的审查者。数据是否可执行、测试集是否仍然独立、指标是否测到目标行为，往往比“再试一种参数”更值得优先检查。

红队的判断也仍然只是待验证假设，最终仍要由编译器、测试和真实报告裁决。

最后，我自己的参与方式也变了。以前看到 AI 给出的代码，我更容易直接复制执行；现在我会先检查输入、输出、路径、配置和副作用，也会主动质疑实验顺序和结论边界。

这三天没有给我一个能修 Java 的 0.6B 模型，却让我开始真正参与实验设计：提出假设、质疑方向、检查代码、邀请红队，最后决定停止。

## 十五、后续：4B 可以继续，但不能换个模型就忘掉这些证据

4B 并不是第一次出现在这个实验里。第二天它已经参与过完整方法、Math-2 行为证据、thinking 和 Lang-33 对照，没有带来真实修复通过。

如果后续再次使用 4B，那是在新的 static 成对规则任务上重新校准，而不是“第一次拿大模型来试”。

当前能够下的结论只是：

> **在当前数据规模、训练目标、LoRA 配置和实验预算内，我没有教会 0.6B 形成可迁移的 Java 规则能力。继续沿现有路线加码，缺少证据支持。**

这不等于证明 0.6B 永远学不会 Java，也不等于已经完成它的基座能力终审。

后续对照仍应使用相同的成对题、短提示词、候选评分、javac 和微型修复，并同时记录实现、精度、显存和耗时。否则，最后看到的差异不一定来自参数量。

后续还可以参考 Nan Jiang 等人的 ICSE 2023 论文 **Impact of Code Language Models on Automated Program Repair**（[arXiv:2302.05020](https://arxiv.org/abs/2302.05020)）。

这篇论文在 4 个基准、442 个 Java single-hunk 缺陷上评估 10 个代码模型，有几个结论与这次实验的方法论很契合：

- 修复能力需要通过测试和语义检查，而不是只看 BLEU；
- 更多微调数据不一定带来更好结果；
- 给出缺陷行不一定有帮助，模型也可能过度依赖缺陷行；
- 模型规模、预训练方式、微调方式、时间和显存成本都应该一起评估。

但论文使用约 129,300 条 APR 训练实例、每个缺陷检查 Top-10 候选，与我的小样本 LoRA 和单次贪心修复不是同一种实验口径，不能直接拿修复率横比。

这次收官不是因为“实验失败，所以算了”，而是因为继续沿原路投入已经缺少新证据支撑。真正应该带往下一阶段的，不是更大的期待，而是这套已经验证过的实验方法。

**模型内部可以是黑盒，但数据、输入、数值、优化、产物和评估，应该逐层变成白盒。先确保基础是好的，再讨论上层；先让每一步都有证据，再让结论往前走。**
