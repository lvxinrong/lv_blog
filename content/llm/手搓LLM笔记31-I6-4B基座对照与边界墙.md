这篇承接 [笔记 30：I6-3 先验证模型会不会 Java](/llm/llm-30-i6-3-java-basics/)，也接在 [I6-1～I6-3 三天总结](/llm/llm-06b-java-three-day-repair-retro/) 之后。

昨天 0.6B 收官时，留下的最后一个问题是：如果换成 4B，在相同的基础题、成对规则和微型修复上，结果会怎样？

今天只评估原始 Qwen3-4B，不加载任何微调结果，不训练 4B。

```text
模型：Qwen3-4B 官方原始权重
精度：BF16
解码：贪心，单轮 Pass@1
提示词：沿用已有基线
评估器：沿用已有 javac、断言与成对规则链路
运行环境：Windows + WSL2 + RTX 4070 Ti 12 GB
```

前两天已经在 Defects4J 完整方法、Math-2 行为证据、thinking 和 Lang-33 上做过 4B 对照，今天不重复那些实验。

## 一、J0 基础生成：从 2/6 到 5/6

第一道对照是 6 道 Java 基础生成题，与原始 0.6B 使用相同提示词和评估器。

结果：

| 题目 | 4B 结果 |
| --- | --- |
| add | passed |
| maxOfTwo | passed |
| sumArray | passed |
| countEven | passed |
| toUpperCase | compile_failed |
| divideAsDouble | passed |

```text
原始 0.6B：2/6 behavior passed
原始 4B：  5/6 behavior passed
```

4B 额外完成了数组求和、统计偶数和 double 除法。它在完整代码生成、数组逻辑与类型转换上的基座能力明显更强。

唯一失败的 `toUpperCase` 也很有信息量。4B 实际生成了：

```java
public static String toUpperCase(String text) {
    if (text == null) {
        return null;
    }
    return text.toUpperCase(Locale.ENGLISH);
}
```

null 判断与大写转换逻辑都正确，但 `Locale` 没有导入，因此编译失败：

```text
cannot find symbol
symbol: variable Locale
```

不能事后补上 import 再把它记为通过。准确结论是：**方法语义基本合理，但自包含代码生成仍然存在缺口。**

## 二、概念题：4B 更强，但仍会犯基础错误

6 道概念题的结果并非全部通过。

### J0-K01：static 核心方向正确，但不完整

4B 正确说明 static 方法和 static 变量属于类，也知道 static 方法不能直接访问非 static 成员。

但没有说明 static 字段由实例共享，也没有补充“可以通过显式对象引用访问实例成员”，所以只算部分正确。

### J0-K02：final 仍然答错

4B 判断以下代码可以编译：

```java
final int x = 1;
x = 2;
```

它仍然认为初始化后还能再赋值一次，与 0.6B 的关键错误一致。

### J0-K03～K06：核心概念基本正确

- 整数除法结果 `1 / 2 = 0` 正确，改成 `1.0 / 2` 得到 0.5 也正确；“向下取整”的措辞不够严谨，但不影响本例。
- `new String("a") == new String("a")` 为 false，equals 为 true，回答正确。
- 数组 `length` 与字符串 `length()` 的结果和区别正确。
- overload 与 override 的核心定义正确。

其中 K03、K06 在 128 token 处截断，属于输出预算问题，不能把已经给出的正确核心答案改判为概念错误，也不能把截断忽略成完整输出通过。

## 三、代码阅读：知道异常名词，不等于能执行代码

### R01：static 编译判断正确

4B 正确识别 static 方法不能直接修改实例字段 `count`，需要通过对象访问。

### R02：null 行为仍然答错

面对 null 元素调用 `toUpperCase()`，4B 回答会输出：

```text
A
null
C
```

它一边提到 `NullPointerException`，一边又声称 null 会被直接打印，随后继续输出 C。

正确行为是先输出 A，在处理 null 元素时抛出 `NullPointerException`，不会继续输出 C。

这再次说明：能说出异常名称，不等于能把规则应用到代码执行上。

### R03：数组越界识别正确，但答案不完整

4B 正确识别 `i == values.length` 时会发生 `ArrayIndexOutOfBoundsException`，但遗漏了异常前依次输出 1、2、3，也没有给出 `i < values.length` 的修复方式，算部分正确。

因此，4B 的基座画像不是“Java 已掌握”，而是：

```text
完整生成、数组逻辑、类型转换、引用比较：明显更强
static 直接访问与数组越界：有所改善
final 重新赋值与 null 执行：仍然错误
```

## 四、static 成对规则：0.6B 的 0/4，到 4B 的 4/4

接下来复用昨天最关键的一组实验：static 方法直接访问实例字段与通过显式对象引用访问的成对题。

每对代码只改变：

```java
return balance;
```

与：

```java
return w.balance;
```

标签由 javac 验证。评估同时检查自由短答案和两个候选答案的模型分数，必须整对都正确才算掌握。

### 开发集

```text
generation_correct_pairs：4/4
score_correct_pairs：4/4
generation_same_answer_pairs：0/4
score_same_answer_pairs：0/4
```

### 最终集

```text
generation_correct_pairs：4/4
score_correct_pairs：4/4
generation_same_answer_pairs：0/4
score_same_answer_pairs：0/4
```

合法与非法版本的候选分数间距也很大，不是勉强压线。

将同一组任务放在一起看：

| 模型状态 | 开发集成对正确 | 最终集成对正确 |
| --- | ---: | ---: |
| 原始 0.6B | 0/4 | 未运行 |
| 旧 static 微调 0.6B | 0/4 | 未运行 |
| 短标签微调 0.6B | 训练集来源为开发对 | 0/4 |
| 原始 4B | 4/4 | 4/4 |

这组结果证明：成对题本身具有可区分性，0.6B 的失败不能简单归咎于题目无法表达或 javac 标签错误。

**4B 不经过任何微调，已经能够在这条规则上完成未见代码的迁移判断。**

## 五、Thermostat 微型修复：第一次完整通过

最后使用与 0.6B 收官完全相同的 Thermostat 微型修复。

模型需要输出一个 replace JSON，要求 old_text 唯一匹配，只进行一次局部替换；之后由评估器编译并运行断言，确认 `Thermostat.read(t)` 返回传入对象的 degrees。

4B 输出：

```json
{
  "action": "replace",
  "old_text": "static int read(Thermostat t) {\n        return degrees;\n    }",
  "new_text": "static int read(Thermostat t) {\n        return t.degrees;\n    }"
}
```

评估结果：

```text
evaluation_status：passed
repair_passed：True
validation_error：None
javac：通过
运行断言：通过
```

这不是“回答看起来像修复”，而是完整通过：

```text
合法 JSON
→ 原文唯一匹配
→ 局部替换
→ javac 编译
→ 运行断言
```

至此，原始 4B 完成了昨天 0.6B 未能完成的最小闭环：**无需微调，在未见成对题上判断正确，并修复一个未见微型缺陷。**

## 六、今天的真实感受：像跨过了一条河

今天最强烈的感受不是简单的“4B 分数更高”，而是震惊。

之前只是抽象地知道：模型规模更大，能力通常更强。今天参数规模增加不到 10 倍，但在同一个任务上，看到的变化却像跨过了一条河：

```text
0.6B：反复训练，仍然 0/4，微型修复无法形成候选
4B：不训练，直接 4/4，并把修复编译和行为测试跑通
```

这不像同一个能力曲线上多前进了一点，更像一道门槛被直接跨了过去。

更让我在意的是：此前在 Defects4J 上，4B 与 0.6B 的表现看起来差不多。完整方法协议中，4B 会逐字复制 buggy 方法；Lang-33 上，两者也都没有完成 null 单行修复。

如果只看那些结果，很容易得出“换 4B 也没用”。但逐步把问题收窄以后，两个基座之间的边界墙才显现出来。

这段震惊需要如实保留，但不能直接写成普遍规律。它描述的是本次模型、任务与评估条件下的真实体验，不是一条已经证明的缩放定律。

## 七、为什么此前看不到差距：可能出现了“地板效应”

今天的一个重要认知是：**两个模型在同一批任务上都失败，不代表它们能力相同。**

如果任务对两者都足够难，结果可能同时停留在 0：

```text
0.6B：0
4B：0
```

这更像评估的地板效应：任务难度已经压平了可观察差异。

当问题逐步收窄后，才开始看到不同层次：

```text
复杂 Defects4J 修复：两者都可能失败
基础 Java 生成：4B 5/6，0.6B 2/6
static 成对规则：4B 4/4，0.6B 0/4
final 与 null 行为：4B 仍然犯错
```

所以不是一堵墙解释所有任务，而可能是不同能力具有不同门槛。

此前“0.6B 与 4B 差不多”的结论只在那些高难任务与协议下成立；随着分辨率提高，差距才变得可观察。

这也说明收窄任务不是降低实验标准，而是在提高测量分辨率。

## 八、边界仍然必须保留

今天的 4B 结果很有分量，但不能扩张为：

- 4B 已经会 Java；
- 4B 能修所有微型缺陷；
- 4B 能修真实 Defects4J；
- 参数量是全部差异的唯一原因；
- 4B 微调一定能继续提升。

当前只能确认：在这组 J0、概念与代码阅读、static 成对规则和 Thermostat 微型修复上，原始 4B 展现出了明显更强的基座能力。

其中 final、null 和缺少 import 的失败仍然真实存在；真实 Defects4J 的未见最小修复目标仍未完成。

此外，当前测到的是两个模型基座的整体差异。预训练数据、训练策略和其他因素也可能共同作用，不能把全部结果只归因于参数量。

## 九、当前决策与下一步

今天没有进行 4B 微调，也不需要为了这条 static 规则再训练 4B。

如果后续确实要尝试 4B LoRA，RTX 4070 Ti 12 GB 上首先要做的是独立可行性冒烟，而不是直接修改模型路径开始训练：

```text
BF16 加载
→ 统一新增 LoRA 参数 dtype
→ batch size 1
→ 激活检查点
→ 单次 forward / backward / optimizer.step
→ 记录显存与耗时
→ 验证保存与严格重载
```

FP32 的 4B 权重本身约 16 GB，已经超过当前 12 GB 显存；BF16 LoRA 是否能稳定训练也尚未验证。

对于 I6，下一步有两个选择：

1. 用同样的 JSON 局部修复协议，让原始 4B 再跑一次真实 Lang-33，检查合成微型修复能否迁移到真实缺陷；
2. 暂停 I6，保留今天的能力画像，进入第三阶段学习。

Lang-33 尚未按今天的新协议运行，不能提前写成成功或失败。

## 十、今天真正新增的实验认知

昨天我学到“先验证管线，再讨论能力”；今天又补了一条：

> **基座选择本身，就是实验设计中的核心变量。两个基座在高难任务上都失败，不意味着它们在更简单任务上的能力也相同。**

如果只用复杂缺陷做评估，可能永远看不到两者的分界；只有把问题逐步缩小，才能找到一堵具体的边界墙。

今天的震惊是真实的，实验数字也是真实的。接下来需要做的，不是把这堵墙夸大成定律，而是继续用同样可执行、可复核的方式，确认它究竟延伸到哪里。

## 十一、0.6B 的新定位：管线 CI，而不是能力终审

今天最后又形成了一个更稳定的认识：0.6B 不是因为没有跨过 4B 已经跨过的门槛，就失去了价值。

如果用 Java 工程类比，我会这样拆分：

```text
参考实现、错误候选、javac、行为断言
= 单元测试与负向控制

0.6B
= 本地轻量测试模型，用来反复打穿训练与评估管线

4B / 更大的模型
= 在基础设施可信后，验证真正的能力假设

Defects4J 等真实基准
= 最终系统验收
```

0.6B 的优势恰恰在于便宜、本地、迭代快。它可以反复用于：

- 检查数据清洗与角色隔离；
- 进行 1 步、32 步或 8 条样本过拟合；
- 检查 mask、loss、保存、加载、Prompt 与 dtype；
- 暴露参考实现意外替代模型候选等评估器 Bug；
- 在付出大模型训练与推理成本之前，先让外围设施经受真实运行。

因此，0.6B 更像管线 CI 中的低成本测试负载，而不是最终裁判。裁判仍然应该是参考实现、编译器、行为断言和真实报告。

这个类比也有边界。Mock 的行为通常是人为控制的，而小模型仍然具有不确定性；所以 0.6B 不能完全等同于 Mock 数据，更适合称为“本地轻量测试模型”。

同时，测试通过也不能证明外部设施“绝对准确”。它只能说明已覆盖的故障没有再次出现。例如 0.6B 上跑通，不代表 4B 的显存、精度和 LoRA 参数类型也一定正确，仍需模型特定的冒烟测试。

这样，两种模型就不再是“谁垃圾、谁优秀”的对立关系，而是分工不同：

> **用 0.6B 做管线 CI，用 4B 做能力假设验证，用真实基准做最终行为验收。**

0.6B 没有学会目标规则，不意味着它不适合本地验证；4B 展现出更强能力，也不意味着它可以跳过同口径评估。模型规模决定了它们更适合回答什么问题，而工程管线负责让这些回答保持可信。

## 十二、120 题同题基线：0.6B 与 4B 的能力矩阵

此前的 120 道题只完整跑过 4B。100 道原始 L0 题虽然早已用于训练与 validation 构造，却没有完整跑过原始 0.6B 自由生成；20 道旧独立题有历史 0.6B 基线，但为了排除脚本版本差异，本次也一并重新运行。

最终对齐条件为：

```text
模型：原始 0.6B vs 原始 4B，均不加载微调结果
题目：100 道原始 L0 + 20 道旧独立题
提示词：legacy 模式
精度：BF16
解码：贪心
输出预算：128 tokens
```

逐文件校验确认，两边每道题的 prompt、reference_answer 和 scoring_points 完全一致：

```text
prompt/reference equality: passed
```

### 生成状态不等于正确率

| 数据组      | 0.6B generated | 0.6B length_limited | 4B generated | 4B length_limited |
| -------- | -------------: | ------------------: | -----------: | ----------------: |
| 原始 100 题 |             97 |                   3 |           92 |                 8 |
| 旧独立 20 题 |             19 |                   1 |           16 |                 4 |
| **合计**   |        **116** |               **4** |      **108** |            **12** |

0.6B 更常在预算内结束，4B 的解释更长、截断更多，但后续人工复核显示 4B 的核心正确数明显更高。因此，正常结束、输出短和格式完整都不能作为能力更强的代理指标。

length_limited 也不能一律判错：部分截断题在耗尽预算前已经给出正确核心答案，另一些则同时存在概念错误，必须逐题检查。

### 人工评分口径

每题按 reference_answer 和 scoring_points 复核，分为：

```text
核心正确或基本正确：主要结论与关键规则正确，允许少量遗漏
部分正确：部分结论正确，但理由不完整、错误或自相矛盾
关键错误：主要结论、规则应用或代码行为判断错误
```

评分同时考虑结论和理由，不是只匹配第一句，也不是字符串相似度评分。结果用于当前开发能力画像，不作为通用 Java benchmark 排名。

### 同题结果总表

| 数据组       | 0.6B 核心正确 | 0.6B 部分正确 | 0.6B 关键错误 | 4B 核心正确 | 4B 部分正确 | 4B 关键错误 |
| --------- | --------: | --------: | --------: | ------: | ------: | ------: |
| static 25 |         7 |         5 |        13 |      15 |       2 |       8 |
| final 25  |         6 |         6 |        13 |      16 |       5 |       4 |
| 整数除法 25   |         4 |         5 |        16 |      13 |       7 |       5 |
| equals 25 |         6 |        10 |         9 |      17 |       6 |       2 |
| 旧独立 20    |         1 |         8 |        11 |      10 |       4 |       6 |
| **合计**    |    **24** |    **34** |    **62** |  **71** |  **24** |  **25** |

大致比例：

```text
原始 0.6B：核心正确 20%，部分正确 28%，关键错误 52%
原始 4B：核心正确约 59%，部分正确 20%，关键错误约 21%
```

四个主题均有明显净收益：static 核心正确从 7 提升到 15，final 从 6 到 16，整数除法从 4 到 13，equals 从 6 到 17。其中 final 与整数除法的关键错误下降最明显。

### 不是逐题单调提升

尽管总体差距很大，仍然存在局部倒退：

- `VAL-04`：0.6B 正确输出 false、true，4B 反而输出 false、false。
- `STATIC-003`：0.6B 至少给出“不违反规则”的正确结论，4B 却把合法的 c.items 判成非法。
- `STATIC-011`：0.6B 正确输出 2 2，4B 答成 1 1。
- 整数除法中也有个别题目从“结论部分正确”变成另一种错误，但总体仍大幅改善。

因此，准确说法是：**4B 具有显著净收益，不是每道题都严格优于 0.6B。**

### 共同错误区没有自动消失

即使换成 4B，以下问题仍然反复出现：

- static 共享计数、构造次数与方法调用次数等状态执行；
- final 必须在声明处初始化的误解，以及部分构造路径问题；
- 整数除法后赋给浮点变量会补回小数；
- 某些运算顺序、强制转换位置和负数取整；
- Object.equals、重载与运行时异常；
- 前一句正确、后一句推翻自己的自相矛盾。

例如 4B 虽然比 0.6B 更常先算出整数除法结果，却仍然会把 7 写成 7.5、把 0 写成 0.75，说明“浮点变量补回小数”是它仍然保有的稳定误区。

### 对基座分工的补充

这 120 题进一步支持前面的角色划分，但也补充了边界：

```text
0.6B：低成本管线 CI 与基础设施探针
4B：能力假设验证和下一轮修复实验基座
真实 Defects4J：最终行为验收
```

4B 已经证明值得作为新基座，但 120 题同时说明它的 Java 基础并不稳定，不能直接推导出“换 4B 微调就会成功”。

后续无论进行真实 Lang-33 迁移验收，还是进入第三阶段学习，这组 120 题都应作为已冻结的开发基线保留。后续再调整 Prompt、训练或反馈闭环时，可以复用同一批题检查：哪些共同错误被消除，哪些能力出现回落。

原始报告分别保存在：

```text

data/reports/i6-l0-eval20-0-6b-original-bf16
data/reports/i6-l0-train100-4b-original-bf16
data/reports/i6-l0-eval20-4b-original-bf16
```

## 十三、I6 阶段收官：暂停本地加码，保留长期修复评估线

到这里，I6 可以阶段收官。

这个决定不是因为微调路线已经被完整验证，也不是因为 I6 的目标已经完成，而是基于当前证据与资源约束作出的投入决策：

- 0.6B 当前路线没有形成可迁移的 Java 规则能力；
- 原始 4B 在 static 成对规则和 Thermostat 微型修复上已经无需训练即可成功；
- 120 题证明 4B 基座明显更强，但仍存在大量具体 Java 语义错误；
- RTX 4070 Ti 可以运行 4B 推理，但完整复测与潜在微调的时间成本较高；
- 4B BF16 LoRA 的本地显存、dtype、单步耗时和稳定性尚未完成训练可行性验证；
- 当前继续扫 epochs、学习率、rank 或扩大本地 4B 训练，缺少足够的新假设支撑。

因此，当前状态必须准确记录为：

> **I6 阶段收官，真实 Defects4J 未见缺陷稳定最小修复目标尚未完成。后续先进入第三阶段学习，再在合适算力与明确假设下重新打开 I6。**

### I6 不是一次实验，而是一条长期评估线

整个 I6 可以分成几个相互衔接、但不要求连续执行的阶段：

```text
第一阶段：0.6B + Defects4J
搭建数据、训练、保存、加载、编译和行为评估基础设施

第二阶段：0.6B / 4B 基座对照
建立能力画像，识别模型边界、输出协议影响与任务难度分层

第三阶段：继续学习底层机制
补充新的理论、工具和实验方法

后续阶段：在云端或其他合适算力上重做 4B 微调
验证第三阶段形成的新训练假设，并反哺学习成果
```

第三阶段与 I6 不是割裂的两条路线，而是一个反馈闭环：

```text
第三阶段学到新的机制与方法
→ 形成一个可证伪的 I6 训练假设
→ 云端小规模 4B 对照
→ 用 Defects4J 做行为验收
→ 再把失败原因带回第三阶段继续学习
```

### 云端解决资源约束，不自动解决实验设计

未来算力更充足，也不能把更多数据、更大 rank、更多 epochs 和更大模型一次性全部加上。否则即使结果变化，也无法判断是哪一个改动产生作用。

重新打开 4B 微调前，至少要冻结：

- 核心假设：训练直接修复、规则迁移，还是基于反馈的修正；
- 数据角色：训练、开发与最终保留测试集如何隔离；
- 原始 4B 基线：在相同任务上的已有生成、编译与行为结果；
- 行为验收：补丁应用、编译、触发测试与回归测试；
- 成本预算：先完成小规模时间、显存与费用冒烟，再决定正式训练；
- 停止条件：训练拟合失败、迁移失败和真实修复失败分别如何处理。

训练目标到时不预设仍然沿用概念问答 SFT。更值得根据第三阶段成果评估的候选包括：

```text
buggy 方法 + 测试信息 → 结构化局部修复
当前候选 + 编译 / 测试反馈 → 下一版修复
```

具体选择必须由当时的学习成果和失败证据决定，不提前写成已验证有效的路线。
